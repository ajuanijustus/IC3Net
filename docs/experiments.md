# Running experiments

## Run tables

Experiments are described by run tables in `configs/`, generated by `configs/make_configs.py`. Each line
holds:

```
<label> TAB <arguments for main.py> TAB <estimated hours>
```

Labels name the scenario, architecture and seed, e.g. `tj-hard__matrix_separate__s03`, and become the
checkpoint file name.

| Table | Contents |
|---|---|
| `corrected_sc.tsv` | StarCraft combat and explore 50/50, 7 architectures, seeds 1–10 |
| `corrected_tjpp.tsv` | PP and TJ easy/medium/hard, 7 architectures, seeds 1–10 |
| `corrected_sc_explore75.tsv` | StarCraft explore 75/75, seeds 1–10 (submitted last) |
| `corrected_tjpp_seeds11-20.tsv` | PP and TJ, seeds 11–20 (when the cluster is idle) |

To change the protocol, edit `make_configs.py` and regenerate. Don't edit the tables by hand.

## Architectures

| Label | Flags | Routing | Pathways |
|---|---|---|---|
| `ic` | (none) | none | single, team reward |
| `iric` | `--mean_ratio 0` | none | single, individual reward |
| `commnet` | `--commnet` | broadcast | single |
| `ic3net` | `--ic3net --phase 1` | scalar gate (fixed open on TJ) | single |
| `gated_shared` | `--ic3net --phase 2` | scalar gate | dual, shared encoder |
| `matrix_shared` | `--ic3net --phase 3` | pairwise matrix gate | dual, shared encoder |
| `matrix_separate` | `--ic3net --phase 5` | pairwise matrix gate | dual, separate modules |

Phase 4 computes the same function as phase 5 (`tests/test_phase_equivalence.py`). Only phase 5 also
saves the communication and action modules separately (`<label>_comm.pt`, `<label>_env.pt`).

## Launching on BlueBEAR

Submit from a checkout pinned to the run's code tag, so that tasks starting days later run the same
code:

```bash
cd /rds/projects/b/baberc-human-agent-teaming/Aju/IC3Net && git fetch --tags
git worktree add ../IC3Net-corrected-v1 corrected-v1
cd ../IC3Net-corrected-v1 && mkdir -p slurm_logs
sbatch --array=1-140 --time=2-00:00:00 launch/run_array.sh configs/corrected_sc.tsv   $OUT
sbatch --array=1-420 --time=4-00:00:00 launch/run_array.sh configs/corrected_tjpp.tsv $OUT
```

What the launcher does:
- Array task *k* runs line *k* of the table (comment lines don't count).
- Each run writes `$OUT/<label>` (with snapshots every 500 epochs) and `$OUT/logs/<label>.log`.
- Finished runs get `$OUT/<label>.done`.

Resubmitting the same command is always safe. Finished runs are skipped, and unfinished runs resume
from their checkpoint (`--resume` restores the optimiser, the log and the main-process RNG; workers get
fresh seeds). Add a throttle such as `--array=1-420%40` to limit how many run at once.

Use `DRY_RUN=1 SLURM_ARRAY_TASK_ID=5 bash launch/run_array.sh <table> <out>` to print the command for one task.

## What a checkpoint contains

`torch.load(path)` returns a dict with:
- `policy_net`: the model state dict.
- `trainer`: the optimiser state.
- `log`: per-epoch metrics, each a `utils.LogField` whose `.data` is the series. Keys: `success`,
  `reward`, `steps_taken`, `comm_action` (executed gate rate per agent), `comm_density` (fraction of
  alive pairs with an open link), losses, entropy and `add_rate` (TJ curriculum).
- `args`: every command-line argument.
- `meta`: seed, worker seeds, git SHA and whether the tree was dirty, torch version, run label, SLURM
  ids and the epochs at which the run was resumed.
- `rng`: main-process RNG states.

## Exporting results and fixtures

```bash
python scripts/export_results.py $OUT results_export        # runs/<label>.json + summary.csv
sbatch tests/bear_checks.sh fixtures                         # bridge fixtures -> bridge_fixtures/
```

`summary.csv` has one row per run: final success, reward, steps and link density as the mean of the
last 50 epochs, plus success AUC and the git SHA. The bridge fixtures (env trajectories, model inputs and
outputs, one training batch and its gradients per architecture) are what the modern
re-implementation is tested against for exact equivalence.

## Reproducing the pre-fix numbers

The pre-fix code is tag `legacy-aamas2027`. On current code, `--legacy_gate_resample` reproduces
the pre-fix gate behaviour exactly: `tests/run_stack_checks.sh parity` checks this against the legacy
tag. Note that the submitted runs also had unseeded RNGs, and their TJ medium/hard runs used the easy
road layout.
